# Website Studio: release and operator guide

Website Studio is available at `/studio` and from the dashboard, Command Center, and the overview of an authorized GitHub Hub repository. This release implements the workflow through **review of a real draft**. It does not build, run, preview, deploy, or publish that draft.

## Try the supported workflow

1. In GitHub Hub, connect the GitHub identity that can see the repository. Select its App installation and repository, open the overview, and choose **Open in Website Studio**. Confirm the connection, repository, visibility, default branch, and head, then register it. A workspace can register a GitHub repository ID only once, including archived registrations.
2. Select the project and choose **Analyze current commit**. Analysis runs on an immutable commit. Review the evidence, limitations and paths before planning. Sync repository metadata independently if needed. A newly observed HEAD marks prior analysis stale; if HEAD returns to a previously analyzed commit, that report becomes current again.
3. For a supported potential HTML finding, prefill a plan from the suggested improvement. Otherwise enter an objective and select one existing source file from the analyzed inventory. Check the expected outcome and verification criteria. Saving a plan does not start execution. Changing the scope or recovering from a terminal failure means creating and approving a new plan.
4. For AI on a **public** repository, explicitly opt in through GitHub Hub. To draft, share the exact eligible file at the plan's full commit SHA. Inspect the file before sharing. A repository-level opt-in without a pinned file only permits bounded analysis metadata. Private repositories can be registered and analyzed locally, but their Studio profile and source are not shared with AI.
5. Approve the exact plan. The existing worker claims the associated job; use **Refresh status** or Command Center to see its progress. The worker reads the approved file and saves at most one inert replacement. It cannot invoke a shell, the external publisher, or any other tool in the draft run.
6. Inspect the full unified diff and approve the **draft only**, reject it, or request changes. Review is tied to the stored SHA-256 digest. Approval of the draft is not permission to publish. Use a new, approved plan for a revision. Archive retains the history and pauses Studio work; restore reopens the same registration. A Hub disconnect revokes access and grants without deleting the registration. Account/project deletion and workspace membership removal follow the migration's FK lifecycle; this release has no cross-account transfer or orphan recovery workflow.

**Command Center:** Open it from the Studio project to preselect the project. With the public opt-in, ask for architecture, static SEO/mobile observations, or recommendations based on the analyzed evidence. No analysis/source ingest or edits happen merely by asking in chat: analyze and approve drafting through Studio. For ambiguous projects, select the project in the existing picker. Studio artifacts and review history stay on the Studio page.

## Security and limitations

- Actor, workspace, account, repository and current revision are rechecked before live reads, AI use, and approval/review operations. Studio list results contain only that owner's already registered metadata. Read-only Hub credentials remain encrypted server-side and are not used for publication. Changing installations or roster pages may require finding the repo again in Hub; Studio currently keeps the original selection and fails closed rather than silently rebinding it.
- Analysis downloads at most six bounded text samples. A bounded/truncated tree yields a partial inventory, not a full audit. Path/mode filters exclude known secret paths, symlinks and submodules; GitHub blob identity and text decoding are checked; detected credentials withhold the sample. The scanner is defense in depth, not a guarantee that a source file is secret-free. Store derived evidence, not raw analysis samples. Manifest script **names**, not literal commands, and environment **names**, not values, are reported. Asset entries are paths only. No package install or dependency audit is implied.
- The draft worker has one allowed tool and no generic project memory, shell, network research, or publication tools in its model context. Repository text is untrusted. Exact source, actor, policy grant, plan digest and live job lease are checked; the DB fences duplicate/cancelled writes. Only the opted-in file is passed to the model. Explain the full objective without secrets; ordinary project names and job metadata follow existing workspace sharing rules.
- Draft verification is limited to pinned source selection, a bounded changed text result, digest consistency and credential-pattern filtering. No successful build, lint, tests, browser checks or performance claims are recorded for a connected website. The draft artifact is a real replacement of one existing regular text file in an inert DB record, not a branch, checked-out repository, or a multi-file patch. Creation/deletion, multi-file milestones, automatic replanning, dependency freshness, and rollback of published work are not implemented.

## Preview, publication, and recovery boundaries

**Verification and preview are blocked in this release.** Render's current worker is not an isolation boundary for untrusted code. The existing project namespace runner is intentionally disabled on Render and requires a separately configured project root and approved command presets. A future integration needs an isolated execution host with ephemeral commit-pinned worktrees, bounded CPU/memory/time, no mutable host mounts or production secrets, network isolation, approved build/test manifests, artifact hashes, structured receipts and a separate authenticated, expiring preview origin. Do not point the Render worker at a clone or add `npm install` to a Studio handler.

**Studio publication is not wired.** The existing scoped GitHub publisher requires an independently authorized write credential, workspace/project/base-branch binding, and a filesystem source whose hashes it verifies against a durable approval receipt. Studio has only an inert DB draft and the read-only Hub credential. There is no publication button, write token reuse, or success receipt. To connect this safely, first materialize and verify the reviewed artifact in the isolated host. Bind a separate human approval to the exact verified file hashes, complete diff, base SHA, target repository/branch, commit message, and proposed PR. Use the existing publisher and receipt machinery to create a new branch and draft PR, and preserve partial failures; do not merge, force-push, or overwrite main. Published rollback is not available; it would be a separate reviewed revert PR.

## Staging rollout (operator only)

1. Use a staging Supabase project and staging Render web/worker. Confirm a backup/restore point, the target DB project, current migration ledger, and deployed revisions. Apply pending migrations in order through `0012_github_hub.sql`, then apply `supabase/migrations/0013_website_studio.sql` through the project's normal reviewed SQL migration workflow. Do **not** reset data or use a schema push as a substitute for these SQL migrations. `0013` is additive and revokes browser-role access to all three Studio tables.
2. Keep the same `APP_URL`, encrypted GitHub Hub App settings, and certificate-verified Supabase pooler setup documented in [GitHub Hub](github-hub.md) and [Render database](render-database.md). Both staging web and worker need the same Hub App configuration and encryption key, in their secret stores. Configure a supported provider on the worker and use the existing `GITHUB_HUB_AI_ENABLED=true` on both hosts only if testing explicitly public sharing. Studio introduces no environment variables, production resources or GitHub grants.
3. Deploy the same reviewed branch commit to **both** staging services using existing build/start commands (`npm ci`, `npm run build`, web start and `npm run worker`). Before allowing jobs, run `STAGING_PREFLIGHT=1 STAGING_EXPECTED_REVISION=<reviewed SHA> npm run staging:preflight` from each staging runtime. After startup, rerun from web with `STAGING_REQUIRE_WORKER=1`. See [staging validation](staging-validation.md). Do not give Studio any generic execution or write credentials to make blocked controls appear available.
4. With a disposable public repository and two Xirel members, exercise registration, duplicate prevention, pinned analysis, share→approve→draft→review, and denied cross-owner access. Change HEAD, revoke a share, and try again; stale approval and removed grants must block. Test private analysis with an authorized private repository and verify no AI ingestion. Confirm GitHub remains unchanged. Production rollout is a separate operator decision.

## Local verification

`npm run test:db`, `npm run test:logic`, `npm run test:auth`, `npm run test:sandbox`, `npm run lint`, `npm run typecheck`, production `npm run build`, and `npm run test:staging-web` in both Google-toggle modes. Test fixtures use local database/network substitutes; live GitHub/model probes require a separate staging opt-in. The smoke suite checks protected Studio page/API and does not use a real GitHub account. No production deployment, schema migration, external publish, or provider request is performed by this guide.
