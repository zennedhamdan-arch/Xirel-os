# Website Studio V2: operating guide

Website Studio is at `/studio` and linked from GitHub Hub, the dashboard, and Command Center. V2 adds **working-branch selection and exact-commit execution**. The current Render deployment remains a control plane; its web service and normal worker do not execute repository code.

## Use Studio

1. Open an authorized GitHub Hub repository and choose **Open in Website Studio**. Select a branch explicitly. Studio labels the default, lists branch heads, filters the current page, and offers exact-name lookup for branches not on that page. Each repository and branch pair can be registered only once per workspace; different branches can be separate projects. Project names still follow Xirel's existing workspace uniqueness rules.
2. In **Working branch**, refresh the branch list or compare a candidate with the current branch. Compare reports ahead/behind for the two fetched commit SHAs, not a live moving diff. To switch, acknowledge the effect on old work. Running or queued work must finish or be cancelled first; a switch doesn't discard artifacts. A deleted or inaccessible branch leaves the project and history intact, with no fallback to default. The GitHub Hub connection is read-only: creating a GitHub branch is unavailable.
3. Analyze the selected branch's HEAD. The report is derived from bounded Git tree and file reads. Reports are stored by commit and associated with a branch; another branch with the same SHA cannot substitute for the branch association. An old report is identified when HEAD changes. Review the limitations: static conclusions are not runtime, mobile rendering, or security audit results.
4. Save an improvement plan on an analyzed branch and commit, or prefill a plan from supported HTML findings. For a public repo, explicitly share the **exact file and pinned commit** through GitHub Hub before approving the plan. The existing worker gives the AI the repo, branch, SHA, declared framework, original objective and that one approved file. It saves an inert replacement, never runs scripts or commits to GitHub. Generic workspace memory is still excluded from this restricted AI worker.
5. Review the full diff and approve the **draft only**, reject it, or request changes. The approval binds the repository ID, working branch selection version, source SHA and exact draft digest. Switches invalidate old approvals for new work even if you switch back or both branches share the same SHA. Legacy V1 approvals/drafts survive as history, but their earlier branchless binding cannot authorize new operations. Retrying a failed draft requires a new plan and approval.
6. If a verified companion is configured, choose **Run verification** or **Start static preview** for the current HEAD or a previous commit analyzed on the selected branch. An exact, approved, current draft can be verified or previewed from its review card. See each command's result, logs, exit code and time in **Verification and isolated preview**. Use **Cancel execution** or **Stop preview** as needed. A preview appears only after the loopback GET health check and the app's public HTTPS ingress check. The temporary link is a bearer capability: share only with intended viewers. It expires in ten minutes, can be stopped early, and is not rendered inside Xirel OS. A link already copied can remain usable until stopped or expired, even if the original UI session ends.

**Command Center:** Select the Studio project before asking about its analyzed branch, branches, or deviations from another branch. The existing registry contains `website_get_analysis`, `website_list_branches` (including exact-name lookup and comparison), and the restricted `website_studio_draft`. Branch/analysis tools require the site's owning member and explicit public Hub opt-in. Command Center does not select branches, run builds, create preview links, or publish on behalf of an AI instruction; use the authenticated Studio controls for those actions.

## What runs and where

| Capability | V2 support |
| --- | --- |
| Source | Read-only public GitHub snapshots only, maximum 60 normal files, 48 KB per file and 1 MB combined. No symlinks, submodules, special paths, binary files, incomplete trees or credential-like text. The control plane verifies Git blob bytes before passing data. Unsupported snapshots fail closed, not partial success. Private repository browsing and analysis remain available through authorized Hub access, without AI/executor sharing. |
| Builds and tests | On the companion only: named npm scripts `lint`, `typecheck`, `test`, `test:integration`, `build`, with lifecycle hooks disabled. The exact `package.json` needs operator approval. Without a declared script the result is **not configured**. Packages with dependencies also need a matching SHA-256 npm lockfile and an independently prepared, immutable offline `node_modules` bundle. Studio does not do a network install on the companion. Lockfiles/binaries outside the snapshot limits, other package managers, and unconfigured dependencies are blocked. React/Next.js/Vue/Vite/Node scripts use the same presets if these conditions are met; no blanket compatibility claim. |
| Execution | A non-Render Linux companion, with a startup boundary probe, runs each approved preset in an ephemeral user/mount/network/PID/IPC/UTS namespace plus chroot. Files are copied to a 96 MiB tmpfs. Root capabilities are dropped, host network is absent, process environment is allowlisted, and project/host roots are not mounted. `/usr` and optional offline dependencies are read-only. The reused runner imposes per-process CPU/address-space/file limits, a 30 s command wall time and output cap; the companion caps total execution at 110 s and admits one active build at a time. The example unit adds aggregate CPU, task and memory limits. Use a dedicated disposable VM, no production credentials, and validate its specific Linux kernel and limits before enabling. Namespaces share the host kernel and are not a substitute for that VM. |
| Preview | Static `index.html` snapshots without a package manifest. A separate host/listener serves bounded text assets with CSP sandboxing, no forms, no embedded frames, no browser `connect-src`, and `no-store`. Relative asset URLs are supported under the capability prefix. It serves exact snapshot bytes, not framework build directories or dynamic servers. Static preview checks do not imply the browser executed the site's JavaScript successfully. The status endpoint and app receipt validate the run, branch, commit and draft digest. |
| Publication | **Blocked.** No GitHub write route/token, publication button, branch creation or rollback. A future integration needs an independent repository/branch-scoped publisher authorization, a verified materialized worktree with exact hashes, and a separate human approval receipt for the exact reviewed diff and base SHA. Route through the existing publisher to a new branch and draft PR only; do not enable until tested end to end. |

The companion holds active jobs and preview bytes in memory; restarts discard them. Studio records run identity, provenance and obtained receipts in PostgreSQL. An unconfirmed start remains pollable until the run is found or expires; do not infer a successful build from a queued request. Execution logs are bounded and credential-pattern filtered; this is defense in depth, not a guarantee against every possible secret format. Only the owning workspace member can request snapshots, see receipts, revoke a preview or obtain its link through Studio. Deploy the preview on an unrelated cookie-free domain and redact its capability paths in ingress logs. No shell commands, GitHub bearer, or database credentials are sent by the app; the companion control endpoint receives only its own scoped bearer and a pinned snapshot. The host must not serve any Xirel OS directories, unrelated projects or ambient cloud metadata to build processes.

## Files and architecture

- `supabase/migrations/0014_studio_branches.sql`: backfills V1's saved default branch/source, introduces workspace/repo/branch uniqueness, branch history and version-fenced plan binding. The existing `head` is the last observed selected-branch head; `source_sha` records the last analyzed source, or is null after a switch. Drafts are virtual work artifacts, not actual Git refs.
- `supabase/migrations/0015_studio_executions.sql`: owner-scoped receipt history and one-active-run fence. New tables are RLS-enabled with browser roles revoked. Preflight checks the new columns and grants.
- `src/lib/studio/{branches,service,executor-client,executor-protocol}.ts`, Hub GitHub helpers, Studio DB schema and `/api/studio`: access and repository checks, scoped branch/compare routes, exact snapshot dispatch, receipt validation and execution history.
- Dashboard Studio UI, Studio tool registry, normal worker: branch picker and run/review UI; read-only Command Center branch tool and branch-bound developer drafts.
- `executor/`, `src/lib/execution/sandbox.ts`, `scripts/project-sandbox.sh`: companion control/preview listeners, reused namespace runner and approved presets. `scripts/test-studio-executor.ts` exercises real commands and a real HTTP preview on a local namespace-capable Linux host. Database tests separately exercise the app with mocked GitHub/model/companion transport, including a populated V1 migration.

## Staging rollout (operator only)

1. Verify the staging DB, backup/restore point, and migration ledger. Apply only pending migrations in order through `0013`, then apply `0014` and `0015` in the project's reviewed SQL migration workflow. Do not reset data or use `db:push` as a replacement. Run `STAGING_PREFLIGHT=1 STAGING_EXPECTED_REVISION=<reviewed SHA> npm run staging:preflight` from staging web and worker. Both should deploy the same revision; after startup, rerun with `STAGING_REQUIRE_WORKER=1`. Keep existing GitHub Hub keys and certificate-verified Supabase settings ([GitHub Hub](github-hub.md), [Render database](render-database.md), [staging validation](staging-validation.md)).
2. Branch management needs no new settings. Leave the executor settings absent until the dedicated companion has passed verification on its intended host. On a disposable non-Render Linux VM, use Node 22 at a system path, `npm ci`, unprivileged user namespaces, standard Linux `unshare`, mount/chroot, `setpriv`, `prlimit` and npm utilities. Use an unprivileged dedicated service user. Verify the sample `executor/studio-executor.service.example` or equivalent cgroup limits and server-level controls. Run `npm run test:studio-executor` on that host. Never run the companion with Render variables, an Xirel `DATABASE_URL`, auth/provider tokens or GitHub keys.
3. On the companion set `STUDIO_EXECUTOR_ENABLE=namespaces`, `STUDIO_EXECUTOR_TOKEN` to a newly generated random secret (at least 32 characters), and `STUDIO_PREVIEW_ORIGIN` to a dedicated, unrelated HTTPS origin if enabling previews. Optionally configure `STUDIO_EXEC_MANIFEST_SHA256` for one reviewed manifest and `STUDIO_EXEC_LOCK_SHA256` plus `STUDIO_EXEC_MODULES` for an independently prepared, read-only offline dependency bundle; approve only reviewed npm configuration. Hash the exact UTF-8 file bytes. Start `npm run studio:executor`. The startup isolation probe must pass; if it fails, do not bypass it.
4. Route trusted, restricted TLS ingress on the companion control origin to port **4201**, and public TLS ingress on the distinct, cookie-free preview origin to **4202**. Firewall raw listener ports and allow control requests only from the Xirel server through trusted ingress. Preserve CSP, cache, health headers and TLS verification. Do not log authorization headers or preview capability URLs. On **staging web only**, set `STUDIO_EXECUTOR_ENABLE=verified-companion`, `STUDIO_EXECUTOR_URL` to the trusted companion's HTTPS origin, `STUDIO_EXECUTOR_TOKEN` to the matching secret, and optionally the exact `STUDIO_PREVIEW_ORIGIN`. Do not expose these via `NEXT_PUBLIC_*`. The normal Render worker does not need these settings.
5. Smoke-test two branch registrations, slash branch lookup, branch switch warning, stale approvals, deleted branch, actual build pass/failure and cancellation, a static preview through the public TLS origin, expiry/stop, and denial to another workspace member. Confirm GitHub is unchanged. External companion availability, TLS ingress and real account checks are **deployment validation**, not implied by local tests. To disable if anything fails, remove verified-companion configuration from staging web and stop the companion; branch management and stored history remain.
