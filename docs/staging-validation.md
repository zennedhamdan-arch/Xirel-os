### What was observed about Render

- The checked-in `render.yaml` defines only `xirel-worker`: Node runtime, `NODE_VERSION=22`, starter worker, `npm ci`, `npm run worker`, manual deploy (`autoDeploy: false`). Defaults are concurrency 2, lease 300 s, poll 2 s, heartbeat 15 s, scheduler tick 30 s and shutdown grace 25 s. Claim and heartbeat renewal now share the same 30–3600 s lease bounds; heartbeat spacing is capped at one-third of the lease. The worker needs `DATABASE_URL`; agent processing requires at least one appropriate provider configured. Adaptive retry and authorization are enforced in PostgreSQL and the worker runtime, not by Render's process supervisor.
- There was no Render management connection or dashboard export available. The blueprint is **not** evidence that the service exists, that it uses these settings, or that web and worker currently run the same SHA. GitHub deployment enumeration alone is not a Render deployment inventory. Do not infer settings from the supplied public URL. Some older docs refer to Vercel for web; do not move the actual web service without an approved plan.
- The existing protected `GET /api/system/health?workspaceId=<id>` now exposes `webRevision` to platform admins; worker heartbeats record the full `RENDER_GIT_COMMIT`. For non-Render hosting set `XIREL_APP_REVISION` to the pinned full SHA at runtime. Compare **the same database's** fresh worker heartbeat with the web revision and confirm no other revision reports active heartbeats. Revision labels do not attest code by themselves; check both deployment records.
- Use separate staging credentials and the same **staging Supabase project and compatible schema** for both services. Web also needs `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, a staging `APP_URL` for authentication and matching `NEXT_PUBLIC_APP_URL` for public integration metadata, and server-only `SUPABASE_SERVICE_ROLE_KEY` for privileged flows. `GLOBAL_ADMIN_USER_IDS` is optional and must list staging administrators only. Supabase public auth values are build-time inputs as well as runtime settings. Pick the correct externally supplied Supabase **session** pooler or supported direct route for a persistent worker and the **transaction** pooler where appropriate for bursty web connections; don't assume a fixed port determines the mode. Confirm DNS/IP connectivity on Render. Prepared statements remain off. `DATABASE_SSL_VERIFY=true` enables CA and hostname verification; tested locally with a test-only CA. Legacy `ssl=require` encrypts but postgres.js does not authenticate the peer in that mode. Treat verified TLS on the real staging endpoint as a deployment gate; never disable verification to work around a wrong hostname or trust root.

### Execution security assessment

| Control | Local evidence / boundary |
|---|---|
| Directory/paths | Exact workspace and project binding, current admin/owner for the worker tools, private worker-owned root, deny unsafe path components and dot/secret names, reject traversals and links. Reads use `O_NOFOLLOW`, reject nonregular and multiply-linked files; edits use file hashes and a worktree lock. The sandbox never receives the persistent worktree mount. Do not expose this against untrusted host writers with the same UID; path checks are not an `openat2`-style race-proof boundary. Filename rules are not DLP. Stage only scrubbed data. |
| Credential/network isolation | Live preset used a fresh network/PID/mount namespace; no non-loopback interface, no host environment sentinel or unrelated filesystem path, and `.env` excluded. Chroot, dropped capabilities and `no-new-privileges`; no host `/home`/application tree mounted. Host kernel and read-only `/usr` remain trusted; optional dependency mounts must be dedicated and scrubbed. |
| Limits/termination | Fixture observed CPU rlimit 20 seconds and virtual address space rlimit 3 GiB, per process (not aggregate). 96 MiB tmpfs, capped snapshot sizes, PID namespace, 24,000 aggregate stream bytes, and 30 seconds from spawn. Actual real deadline, cancellation, and output termination passed. No aggregate memory/CPU/PID exhaustion guarantee or hostile-code sandbox certification. |
| Commands/audit | No arbitrary shell API. Presets only; npm scripts require an operator-pinned package manifest, with implicit pre/post disabled. Tests/builds still execute project code. Persisted start/terminal status, exit code and byte counts checked against the run. Captured output is used in the active tool turn, not persisted verbatim. |

**Native Render:** keep all `AGENT_EXEC_*` variables and the write token unset until appropriate infrastructure is approved. With `RENDER` present the namespace command is not offered and execution refuses even if configured. For a hosted execution lane, use a separate disposable Linux VM or a reviewed sandboxed runner with a dedicated non-root UID, aggregate cgroup v2 CPU/memory/PID limits, constrained mounts, syscall policy, no network by default, no runtime credential mounts, and per-job teardown. Validate it on the actual target image before connecting it to a worker. There is no managed remote runner included here.

## Throwaway personal project run

`npm run test:db` creates a dedicated `Staging Addition Fixture` project with the actual project API on throwaway PostgreSQL. The test uses simulated Supabase identity and a scripted AI response, not an external model. It names the project in a natural-language objective and explicitly selects its authorized project ID for file access. **The model does not get to grant itself worktree access by choosing a project.** The production runtime, plan persistence, local file tools, Linux runner, SQL, and API route handlers are real.

1. Stored a project decision and submitted “In Staging Addition Fixture, repair the addition helper, run the existing test, and report the result” through the protected job route.
2. Persisted a three-step plan, resolved the named project, returned the seeded decision from project memory, and read the authorized `addition.js` and SHA-256.
3. The real isolated test failed because the helper subtracted; worker audit recorded exit 1. The scripted provider used the tool output and prior hash to request the exact-match repair. The runtime re-read the repaired hash and ran the preset again; audit recorded exit 0.
4. Checked the authorized run-detail route for the pinned project, plan steps, both command results, and completed response step; checked the corrected worktree contents and changed hash separately. A scripted response does not establish live model diagnosis quality.
5. Submitted a separate publication job for that exact path/hash against the fixed fixture repo/base. Verified `waiting_approval`, persisted exact receipt, and **no outgoing publication request before approval**. Exercised the protected approval route and the resumed worker against a GitHub transport mock. Checked branch/commit/draft request, report, no autonomous replay, and separate partial-PR-failure reporting. Live GitHub write was deliberately not exercised.

The separate process-level worker test exercises the actual worker poll loop, Gemini adapter, PostgreSQL and TLS client with synthetic fetch replies. The retry test asserts a future due time before advancing that one fixture row's timestamp; it does not claim to have waited through the full backoff interval. SQL establishes the cancellation fence in that subprocess test; the lease loop detects it and aborts the pending fetch. A 401 is no longer mislabeled as a transient timeout: text routing preserves a sanitized failure class; 503 schedules a bounded retry, and jobs with a write-attempt marker are not replayed automatically.

## Provider probes and model evaluation

`npm run test:providers` sends no requests unless `STAGING_LIVE_TESTS=1` and `STAGING_PROBES` is explicit. Inject credentials through the staging secret store or shell environment, not command arguments, code, a shared report, or browser-facing variables. The command emits only test labels/statuses, timings, safe failure classes, and dimensions. It sends fixed benign synthetic inputs, not worktree data or project memory. No model-produced code is executed and the GitHub probes are read-only. Exit `0`: all selected assertions passed; `1`: one or more failures; `2`: not run or one or more selected checks skipped. Tests can consume quota or incur cost.

```sh
STAGING_LIVE_TESTS=1 STAGING_PROBES=openrouter,gemini,embeddings,rerank,failure \
  STAGING_OPENROUTER_MODELS=lightning,gemma26,gemma31,omni npm run test:providers
STAGING_LIVE_TESTS=1 STAGING_PROBES=github,brave,page npm run test:providers
```

| Probe | Assertions and this run's outcome |
|---|---|
| OpenRouter chat (Lightning, Gemma 26B, Gemma 31B, Nano Omni, or configured route) | Tool name and exact numeric argument; schema parse and arithmetic correctness where documented; deterministic-form coding fix and recovery label in a multi-kilobyte context. One sample per metric is screening, not a benchmark. **Not tested live: no key.** Schema probe is skipped for Omni by default. |
| Gemini | Same benign probes through Gemini, including its structured-output path. **Not tested live: no key.** Actual adapter parsed fixture responses and handled 401/503/cancellation in worker. |
| OpenRouter embeddings / rerank | Separate endpoints, ordered vector indices, 2,048 dimensions and semantic similarity; relevant candidate first and score order. **Not tested live: no key/role config; mocked response handling exercised.** |
| OpenRouter failure | One intentional non-existent model expects 400/404, not a fabricated successful answer. **Not tested live: no key.** Runtime retry classification was exercised separately. |
| GitHub | **Passed live:** authorized fork repository read (~633 ms), shared README (~218 ms), commit diff response (~494 ms), check-runs response (~279 ms) using the workspace GitHub authorization for this read-only probe. This verifies retrieval, not that any CI check ran or passed. A scoped staging read token is required in deployment. Branch/commit/draft and partial failure are **mocked only**. |
| Brave and page retrieval | **Brave not tested live: no key.** Search request/response path mocked. Separate real HTTPS retrieval of `https://github.com/github` succeeded with hostname/certificate validation and bounded extracted text. This is not proof of a live Brave-to-page flow. |

Run each configured model several times with a representative staged development task, measure median and tail latency, and record tool/schema success and grounded repair correctness before recommending changes. Also confirm availability and rate/credit limits for the account. No default provider or model was changed by this mission.

## Recommended staging rollout (manual; no steps performed on Render)

1. In the Render dashboard, inventory the existing web and worker service IDs, source repositories, current SHA, build/start commands, environment **names only**, plan, networking and auto-deploy settings. Separately confirm the current web hosting platform if it is not defined in Render. Use a staging-only web service and workspace with non-production credentials, manual deploy, and no automation that promotes commits. Pin both to the same reviewed full SHA. Run `npm ci` and build web with `npm run build`; on Render start with `npm run start -- --hostname 0.0.0.0 --port "$PORT"`. For the staging worker use the blueprint npm command or the equivalent direct Node start (`node --conditions=react-server --env-file-if-exists=.env.local --import tsx worker/index.ts`) so the single process receives SIGTERM. Verify shutdown behavior on the actual service.
2. Confirm the database is a dedicated staging Supabase project; snapshot any preexisting test data and compare migration ledger and grants. Fresh databases: review/apply 0001–0011 in order. Existing schema: apply **only pending** reviewed migrations; do not reset, reapply blindly, or use `db:push` against a shared database. Check that auth users, project memory and Business OS records remain intact and confirm the runtime role can access required records.
3. Before allowing traffic or jobs, in **both staging runtime environments** set `STAGING_EXPECTED_REVISION` to the reviewed SHA and run `STAGING_PREFLIGHT=1 npm run staging:preflight`. It performs a read-only schema, TLS and grant check without printing the DSN. Match the real service revisions and database project reference in the dashboard. Launch worker without optional worktree/command/write settings. After startup, rerun from web with `STAGING_REQUIRE_WORKER=1 STAGING_PREFLIGHT=1 npm run staging:preflight`; require a matching fresh worker row and check the protected health view for older workers and job backlog. The preflight is a sentinel check, not migration history verification or a substitute for exercising RLS with staging users.
4. Smoke test staging login and OAuth redirect allowlists, two-workspace isolation, project memory, Business OS, a harmless scheduled/durable job, cancellation while running and recoverable retry. Verify queue/task/lease records, approvals and heartbeat freshness in the staging database. Then run the credential-gated probes from the real runtime network. Turn on GitHub **read** first. Only request write access after review of a scratch repository with no deploy triggers; require explicit approval and inspect reported effects. Use a separately reviewed isolated worker for worktree/test acceptance; **do not change the Render execution gate to make the test pass**.
5. Review the evidence before requesting any promotion. To back out, pause/suspend the staging worker and disable connector credentials first; use the compatible previous web and worker revisions only after reviewing schema compatibility. Preserve database history and inspect interrupted or partial external writes manually. Do not replay receipts, reset production, merge upstream, or deploy without authorization.
