# GitHub Hub — multi-account, read-only

Open **GitHub Hub** from Dashboard or Command Center. The Hub is part of your existing Xirel workspace and uses your normal Xirel sign-in. A Hub connection is **not** another Xirel login, and signing into Xirel through GitHub does not authorize the Hub. Each connection belongs to the signed-in Xirel user in the selected workspace. Neither peers nor workspace administrators inherit its credentials or discovery results. A member may explicitly connect the same GitHub identity again in a different workspace; lists and grants remain separate.

## Configure a staged GitHub App

1. Create a **separate GitHub App** for the Hub, preferably one per environment. Grant repository **Metadata**, **Contents**, **Issues**, and **Pull requests**: **Read-only**. Do not grant organization or account permissions, request broad OAuth `repo` scopes, upload a private key to Xirel, or enable webhooks or write permissions. Choose an installation visibility policy that permits the intended personal accounts and organizations to install it. If installation is limited to the owning account, it cannot be installed into the other accounts. For an organization, an authorized owner may need to approve/install the App and select its repositories.
2. Set the App's **Callback URL** to `${APP_URL}/api/github-hub/callback` (for production, `https://xirel-os.onrender.com/api/github-hub/callback`). This is distinct from the Supabase callback for Xirel sign-in. Leave **Request user authorization (OAuth) during installation** off: first install or configure the App, then start authorization in Xirel so the callback can validate state and the selected workspace. Use expiring App user tokens.
3. Set the following on the **web service**, in its secret store, never as `NEXT_PUBLIC_*` values. The worker needs only the App client ID, the encryption key, and the sharing flag if it is approved to read Hub data; it needs no Hub OAuth client secret.

| Setting | Purpose |
| --- | --- |
| `APP_URL` | Canonical HTTPS Xirel origin, matching the App callback and form origin. |
| `GITHUB_HUB_APP_SLUG` | App slug used to link to GitHub's install/settings workflow. |
| `GITHUB_HUB_CLIENT_ID`, `GITHUB_HUB_CLIENT_SECRET` | App **client** credentials (not the numeric App ID, not a PAT, not the login OAuth provider secret). |
| `GITHUB_HUB_ENCRYPTION_KEY` | Standard base64 encoding of 32 random bytes (for example, generate with `openssl rand -base64 32` in a secure terminal and transfer directly to the secret store). Keep it stable across web instances and any approved worker against that database. Separate environments. Losing/changing it or changing the App client ID requires reconnecting existing accounts. |
| `GITHUB_HUB_AI_ENABLED` | Unset/false by default. Set `true` on an approved web service to allow explicit sharing and use by interactive agents, or additionally on the approved worker for queued jobs. Do not set it where provider data handling has not been approved. |

4. Use the Hub's GitHub install link and select repositories for each relevant personal account or organization. Return to Xirel, choose **Connect account**, and use GitHub's account picker. Repeat and verify the second username. The same GitHub user ID updates its existing connection in that workspace, while **Reconnect** refuses to replace it with a different identity. If you do not see an installation, confirm repository selection, organization approval/SSO and that this specific GitHub identity has access. An install by itself does not grant every connected identity access.

References: [GitHub App user OAuth and PKCE](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app) and [GitHub user-token installation and repository discovery](https://docs.github.com/en/rest/apps/installations?apiVersion=2022-11-28).

## Behaviour and boundaries

- The browser receives the public App authorization URL, sanitized account metadata, and requested repository data—not Hub tokens or encryption keys. OAuth state is bound to a short-lived HttpOnly browser cookie, an authenticated Xirel user and workspace, and an encrypted PKCE verifier. The callback atomically claims state before exchange and verifies the stable GitHub user ID before storing the credential. Tokens use AES-256-GCM with associated data binding the App, workspace, actor and GitHub identity. No refresh token is stored; reconnect when GitHub's short-lived user token expires or is revoked. **Disconnect** removes the local ciphertext and associated AI grants, cancels pending local OAuth flows for that workspace user, and keeps a disconnected account entry for reconnect. It does not uninstall the App or revoke your global GitHub grant; use GitHub’s settings if you also want that.
- Discovery uses GitHub App **user** access tokens, not a service PAT or standalone installation token. GitHub determines the intersection of the user's access and the App installation's selected repositories. Every explorer request rechecks both installation and repository access with the **same** account token. App installations with permissions outside the supported read-only list are blocked. Select installations separately; search/filter pages inspect up to 60 accessible repositories at a time. Continue through pages when matches are sparse. If GitHub reorders a roster after a grant or selection, refresh discovery and re-save the grant from the repository’s current page. Directory browsing uses the default branch; text previews are limited to 16 KB UTF-8, and GitHub caps directory results at 1,000 entries. The commit view shows change totals and filenames, not an unrestricted patch. Issues and pull requests show summary metadata and link to GitHub for further detail.
- **No GitHub repository writes** are implemented by the Hub. The existing, separate `github_publish_change` tool is unchanged: it still requires its own explicit project configuration and exact-argument approval receipts. A Hub credential cannot enable it. Web/API account management uses existing workspace guards; the agent/worker uses the same membership lookup. The Hub tables have RLS and no browser role grants, and accounts cascade out on workspace-membership removal. `github_hub_audit` records only IDs, operation, outcome, and timestamp; agent invocations additionally use the normal tool execution audit. Avoid storing or exporting full callback URLs or query strings in proxy logs.
- **AI sharing is off by default and private/internal repositories stay browser-only.** With the server flag enabled, an account owner may explicitly grant a **public** repository's metadata and up to five reviewed paths at one exact commit SHA. A server check validates the pinned regular files and rejects likely credentials before saving. Tool reads recheck the actor, GitHub repository access and share; regular blobs only, no symlink/submodule resolution, 16 KB input and an 8,000-character text excerpt cap. The credential detector is defense in depth, not a proof a file is safe: review paths and their pinned contents manually. Provider calls never receive Hub access tokens. Shared excerpts/metadata can be retained in the existing agent/tool conversation history; stopping sharing prevents future reads, not recall of prior output. Hub reads do not automatically write to project memory.

In Command Center, for example: **“Use `github_hub_read` to find the shared architecture repository and summarize the pinned README and recent commits. Cite source links and separate observed facts from assumptions.”** Only this actor’s explicitly shared public repositories are discoverable by the tool. `find` searches name/description in bounded pages, and returns the account/repository pair to use for follow-up calls.

## Manual release and staging checklist

- Review the branch and [Render DB setup](render-database.md). In a dedicated staging Supabase project, apply only pending migrations in order, including `0012_github_hub.sql`. It adds Hub-only tables; no existing schema/data is reset or copied. Do not use a production reset or `db:push` as a release step.
- Configure the separate staging GitHub App and staging web secrets above. After approval, deploy the pinned branch revision to staging. Leave AI sharing off for the initial validation. In a staging browser, connect two distinct real identities, check each username/avatar, verify one personal repository and one authorized organization repository, and confirm a repository absent from its installation cannot be selected. Check search, file browsing, commits, issues, PRs, disconnect/reconnect, and that a second Xirel user cannot use the first user's connections.
- If approved, enable sharing in staging, create an explicit public grant with a reviewed pinned file, and use Command Center to run the tool. Confirm no private/internal repository is shareable, no agent read is possible before granting access, and stopping sharing/disconnecting denies subsequent reads. Roll out to production only by a separately approved manual deployment. App config and migration are not applied by publishing the Git branch.

## Implementation test report

- `npm run test:db` covers the Hub in real disposable PostgreSQL with **mocked GitHub HTTP and a substituted Supabase session**. Cases cover migration install/reapply and main app preservation, browser-bound PKCE/state, two GitHub identities, account attribution across personal/organization repositories, search and pagination, repository and workspace denial, encryption/redaction, rate limits, bounded files, read-only tool output, credential detection, sharing and disconnect/reconnect.
- Local Chromium against a production Next build, disposable PostgreSQL and **simulated GitHub consent/API and Supabase session** exercised both account connections, explorer views, mobile viewport overflow, organization discovery and disconnect/reconnect.
- Production build, lint, typecheck, core logic and auth regression checks passed locally. No live GitHub App or two-account grants were available for real validation. No production configuration, migration, deployment, or GitHub repository changes were made.
